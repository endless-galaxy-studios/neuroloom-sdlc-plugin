## [0.7.0] - 2026-11-23

### Breaking Changes

- **The SDLC root is `ops/sdlc` again, and `.claude/sdlc` is no longer supported.** CD's decision, 2026-11-23. z-sdlc's factory treats `.claude/` as protected agent configuration: its implement guard refuses any path with a `.claude` segment, and its tool policy denies edits there, so a `.claude/sdlc` root can't take part in the factory. The move to `.claude/sdlc` came from Neuroloom D26 (2026-03-28) and was about co-location only. There is no compatibility path.
- **A project whose root is still `.claude/sdlc` must move it before running `/sdlc-migrate` or `/sdlc-port` on this version.** Move the contents of `.claude/sdlc/` into `ops/sdlc/` with `git mv` (or stage the move); in `.sdlc-manifest.json` set `"sdlc_root": "ops/sdlc"` and re-key the `installed_files` and `declined_files` entries to `ops/sdlc/` paths and update the `bundle_fragments` target paths; commit the move; and update the live references that name `.claude/sdlc/` (`CLAUDE.md`, `.claude/agents/`, `.claude/skills/`, `.claude/agent-memory/`). Until then the new root check halts both skills (below).
- **Requires z-sdlc 3.0.0**, which carries contracts 0023 to 0026. 0023 drops the `.claude/sdlc` root upstream too. 0024 and 0026 make the knowledge layer the adapter's, file by file: `knowledge-seed` removes the map and `sdlc-initialize` Phase 1's copies of the knowledge and discipline files it seeds (their `installed_files` entries dropped, not declined), `knowledge-update` takes the copies a migration makes of what Neuroloom holds (only a file entries name, every one of which it checked this run; never a discipline file, whose status and structure no delta carries), lists the copies it can't confirm and the files an older port removed that Neuroloom doesn't hold, and removes a leftover map only when git shows it unmodified, initialize hands the project's own knowledge to the new `project-knowledge` phase, and `sdlc-migrate` leaves alone each file the plugin took (off disk, no entry, not declined) and treats the rest as ordinary files. What Neuroloom doesn't hold (READMEs, diagrams, `provenance_log.md`, files the project edited) stays on disk, including after the port's Post-Port Cleanup. 0025 names the adapter by its plugin id, `neuroloom-sdlc@endless-galaxy-studios`, and finds the enabled install on every run, so the manifest records no install path. `adapter.json` and `plugin.json` declare it (`supported_zsdlc_version: 3.0.0`); `adapter.json` no longer carries the pre-rename `ccsdlc_adapter` and `supported_ccsdlc_version` keys. Initialize now finds the adapter before Phase 1's copies, so `post-file-write` runs on each, before the project's agents exist: the transformer's stale-agent audit only warns there, and the initialize audit re-runs it against the final roster and lists what still doesn't resolve. z-sdlc runs `post-file-write` on `CLAUDE.md` once Phase 2 saves it. A halt in any handler ends a headless run `failed`. An older z-sdlc release can't find a plugin the port registered this way (it looks for `plugin_root`) and stops before any phase, which is safe; install the required release first. Upgrading the plugin is `claude plugin update`. Optionally, delete an absolute `adapter.plugin_root` from the manifest: z-sdlc 3.0.0 never uses one and its migrate removes it, and a relative one names a copy vendored in the project and stays. z-sdlc releases before 0025 load the adapter's handlers from that path, so a path left from an earlier install runs that version's handlers instead of this one's (Sleeved's points at the 0.6.1 install); without it, such a release can't find the plugin and stops before any phase. The SessionStart hook warns while an absolute path is set. Then check that `claude plugin list --json` in the project shows 0.7.0 enabled, and don't override `sdlc-migrate`'s adapter version gate on this upgrade: with 0.6.1 still enabled, an override would run 0.6.1's handlers, which have none of 0.7.0's halts.

### Changed

- **`/sdlc-port` transforms what its audit checks.** Stage 4a now scans every `*.md` under `ops/sdlc/` outside `knowledge/` and `disciplines/`, as well as `.claude/agents/` and `.claude/skills/`, and looks for the `[sdlc-root]/knowledge/` and `[sdlc-root]/disciplines/` forms, relative links and `provenance_log` mentions, besides the written-out paths and bare YAML names it already matched. Before, the audit scanned `.claude/skills/`, `.claude/agents/` and the moved directories for the `[sdlc-root]/` form, which Stage 4a never looked for, so a correct port could fail its own audit. Template placeholder text that names a knowledge path is now transformed too: the audit has no template exemption. Stage 4a, Stage 4d and the verification rows now exempt exactly what the audit scan each one mirrors exempts: the path and bare-YAML checks leave alone the audit's Check 2 exemption rows 1 to 5, and the link and `provenance_log` checks leave alone only the changelog, as Check 2d and the provenance scan do. `process/knowledge-routing.md` is replaced whole with the plugin's Neuroloom variant, as migrations do, and checked against it.
- **`/sdlc-port` no longer moves anything.** Stage 4f, which moved `process/`, `templates/`, `playbooks/`, `examples/`, `plugins/` and `improvement-ideas/` from `ops/sdlc/` to `.claude/sdlc/` and rewrote paths to match, is gone. Stage 4g (the stage letters keep their old names, so there is no 4e or 4f) still rewrites agent-memory references to `ops/sdlc/knowledge/` and `ops/sdlc/disciplines/` into `memory_search` calls; it no longer touches other `ops/sdlc/` paths, which are now correct. The verification checklist drops the rows that demanded the six directories be gone from `ops/sdlc/` and checks they are still there.
- **Post-Port Cleanup removes only files Neuroloom now holds, by path.** Its old "remove all remaining `ops/sdlc/` content" option ran `rm -rf ops/sdlc/`, which was safe only because Stage 4f had emptied the directory. Without 4f it would have deleted the live process docs, templates and playbooks. The option is gone, and the skill now says never to remove `ops/sdlc/` itself. The remaining option no longer runs `rm -rf ops/sdlc/knowledge/` either: it deletes the files Stage 3a's seed file names as sources, the discipline files, the map, and the provenance log when Stage 3c stored every entry. It keeps the knowledge READMEs and any knowledge file nothing ingested, since Neuroloom doesn't hold their text and z-sdlc 3.0.0 would never restore a file off disk (contract 0026), and lists what stays in its question.
- **Every post-operation scan reads `ops/sdlc`** (Checks 1, 2, 2a, 2b, 2d, the provenance scan, the exemption paths) and skips `ops/sdlc/knowledge/` and `ops/sdlc/disciplines/`. Those two hold file-mode data the transformer never rewrites, and on a port they are still on disk when the audit runs, before Post-Port Cleanup. Check 6 now covers both directories: an `agent-context-map.yaml` the run created is a regression; a tracked map, or an uncommitted one `knowledge-update` left in place, is a warning, and so is a copy it listed as likely redundant; what Neuroloom doesn't hold stays on disk and isn't reported. Check 4 requires `sdlc_root` to be `ops/sdlc`.
- **Recoveries cover the SDLC root.** The migrate and port recoveries said `git checkout -- .claude/`, which covered the root only while it sat inside `.claude/`. Migrate's recovery now saves and restores by path across both trees, and the port restores from its own copies (below), never git.

### Fixed

- **`/sdlc-port` deleted z-sdlc's `sdlc-migrate` and `sdlc-initialize` skills.** Its Stage 4e removed `.claude/skills/sdlc-initialize/` and `.claude/skills/sdlc-migrate/` because "the plugin provides its own versions", but the plugin stopped shipping them in May 2026 (`c9c44c2`, when z-sdlc's own skills began calling the adapter handlers). After a port, `/sdlc-migrate` was gone. Stage 4e is removed. A project an earlier version ported may be missing `sdlc-migrate`: copy z-sdlc's `skills/sdlc-migrate/` (every file in it) from the release the project is on into `.claude/skills/`, then dispatch this plugin's `neuroloom-transformer` agent on the copied files, so they read Neuroloom and not the file-mode knowledge layer. `sdlc-initialize` needs nothing: z-sdlc runs it from its source and never installs it. The README and three references still described the old override; they now point at the adapter handlers and the transformer's runtime scan.
- **The port's discipline verification could never pass.** It searched `tags=["sdlc:discipline:architecture"]`, a tag ported entries never carry (they have the bare `sdlc:discipline` tag). It now uses `tag_prefixes=["sdlc:discipline"]`.
- **"Skip this prompt on future re-ports" did nothing,** and a port overwrote the manifest. Nothing read `skip_cleanup_prompt`, and Stage 5 wrote `.sdlc-manifest.json` from a fixed list of keys, dropping a ported install's `installed_files`, `declined_files` and `bundle_fragments`. The option is gone, since a re-port now always skips Post-Port Cleanup, and Stage 5 updates the manifest, keeping every key it doesn't set. It rehashes the `installed_files` entries of the files the port wrote, so the audit's hash check and the next migration's drift check see the port's own edits as expected. Post-Port Cleanup records only the map in `declined_files`: under contract 0024 upstream never asks about a missing knowledge-layer file, and a declined knowledge file would never be seeded again. An unreadable manifest now stops the port instead of being overwritten.
- **A ported project never entered adapter mode.** `sdlc-migrate` decides adapter mode from the manifest's `adapter` block alone, and the port never wrote it, so the next migration ran in file mode: no transforms, flat knowledge files. Stage 5 now writes the block, as `sdlc-initialize` does. A project an earlier version ported and that has no block needs one added by hand (the shape is in `skills/sdlc-port/references/verification-manifest.md` § Write Manifest); if its `source_version` came from that port rather than from a migration, also remove `source_version` and `source_version_sha`, so the next migration runs in full.
- **The port stamped the project with a release its files weren't on.** Stage 5 set `source_version` and `source_version_sha` to the latest z-sdlc release, so the next migration could report "already on" that release and stop. The port no longer touches either; the release it seeded is recorded as `knowledge_seed_version`.
- **`/sdlc-initialize` left an `agent-context-map.yaml` that every later migration had to work around.** z-sdlc's initialize copies the map and wires it, with no adapter exception. The `knowledge-seed` handler now removes it the way z-sdlc removes any framework file a project declines (deleted, recorded in `declined_files`, its `installed_files` entry dropped, so a later migration neither asks about it nor restores it), and tells the rest of the run what stands in for it. Check 6 can then treat a new map as a regression on both operations. A map an earlier initialize left is a warning, with the same removal as the fix.
- **The port wrote provenance records before you confirmed the transformations,** in Stage 4a, and deleted `provenance_log.md` there, while another passage said Post-Port Cleanup removes it. The records are now ingested in a new Stage 3c, after the Stage 2 confirmation, with a duplicate check that also moves a record's status forward when the log is ahead (never back), and the file goes with the rest of `knowledge/` in Post-Port Cleanup. The Stage 4b option that skipped transformations is now **Stop after ingestion**, and it ends the run there, as Cancel does: no manifest write, audit or cleanup. Before, the run went on to write a manifest that called the untransformed project ported, run an audit that failed on the untransformed files, and offer to delete the directories those files still read. What Stage 3 stored stays in Neuroloom.
- **Ported agents couldn't call the tools their rewritten text uses.** The port transformed Knowledge Context sections into `memory_search` calls but never added the Neuroloom MCP tools to the agents' frontmatter, which `post-file-write` does on a migration; z-sdlc's compliance auditor lists only `Read, Glob, Grep, Bash`. Stage 4c now ends with the same tool injection.
- **Smaller port fixes.** Gate 3 no longer treats a project `/sdlc-initialize` set up, or a sentinel from another project, as an interrupted port. The count check no longer says to re-seed one category alone, which would have marked the other category deprecated. Stage 4a rewrites `bundles/README.md` links in a project without `bundles/`, and Stage 4d accepts a relative link whose target exists and stays. An audit failure restores the manifest from a copy Stage 5 takes first. The post-operation audit's minimum-MCP list names `ops/sdlc/templates/agent-template.md`, where z-sdlc installs the agent template, instead of `.claude/agents/AGENT_TEMPLATE.md`.
- **Migration recoveries restored the files but not the manifest.** The post-operation phase is warn-continue, so upstream writes the new `source_version` and hashes after a failed audit; restoring only the files left a manifest saying "already on" the target. The recoveries now include `.sdlc-manifest.json`: on a tree that wasn't clean they change nothing but the manifest, which they put back from the run's snapshot.
- **The port's extractor dropped knowledge, and the cleanup then deleted the source.** 41 of the 94 knowledge YAMLs in Neuroloom's own tree produced no entries: 35 declare `pattern: entries` with no `entries` list, and 6 declare `pattern: rules` but hold `entries`. Files that did parse lost their other top-level sections (z-sdlc's `model-tier-strategy.yaml` lost three) and fields inside items (`source`, `anti_pattern`, `applies_to` and others). Knowledge Markdown documents (z-sdlc's `knowledge/search/*.md`) were never read, and declined knowledge files were seeded. The extractor now keeps every section and field, reads the Markdown documents, and skips declined files (`--manifest`); its dry run lists any file that produced nothing. Every existing `knowledge_id` is unchanged.
- **`CLAUDE.md`'s SDLC region was never transformed.** z-sdlc merges `CLAUDE-SDLC.md` into it, with live reads such as `Read [sdlc-root]/knowledge/coding/comment-discipline.yaml`, and no handler, port stage or audit scan covered the file. `post-file-write`, the port's Stage 4a and the audit's scans now include the lines between `<!-- SDLC-START -->` and `<!-- SDLC-END -->`, and never a line outside them.
- **Knowledge only a file pointed at was out of reach.** `knowledge-seed` and `knowledge-update` ingested knowledge YAMLs only, and agents reached z-sdlc's knowledge Markdown documents only through the map a Neuroloom project removes. Both handlers now ingest them, with the same id and tags the port's extractor uses. `post-file-write` no longer rewrites files under `knowledge/` or `disciplines/`: their content goes to Neuroloom, and a copy on disk is data.
- **`/sdlc-initialize`'s Phases 7 and 8 wrote project knowledge only to disk.** They run after `knowledge-seed`, so the discipline project context and testing gotchas they write never reached Neuroloom, where the agents look. The `project-knowledge` phase (below) now stores them as memories.
- **The audit missed written-out knowledge paths.** Check 2 matched only the `[sdlc-root]/knowledge/` form, so a missed `Read ops/sdlc/knowledge/team.yaml` passed while the cleanup deleted its target. It now matches both forms; z-sdlc's installed files use the written-out form only in files the audit already exempts.
- **Discipline records after a port, and provenance id collisions.** A ported project holds each discipline as one `disciplines:<stem>` entry (the whole file, parking lots included); its first migration creates `discipline:<name>:framework` beside it. `knowledge-update` now says this is two records by design and leaves the port's alone. Stage 3c no longer skips or overwrites a provenance record whose `source` differs from the log entry with the same id (ids are numbered per day, so two branches can reuse one); it lists the id instead.
- **References to the removed `sdlc-migrate` override's stage numbers** ("Stage 4.2", "§4.2.0", "Stage 5.0" and the like) in the recovery reference, the content-merge audits, the post-operation audit and the pre-flight doc now name z-sdlc's real sections or this plugin's handlers. The recovery reference no longer describes a re-initialize mode or early exit z-sdlc doesn't have.
- **The port could not seed a real project.** The API takes at most 500 entries per `sdlc_seed` call; stock z-sdlc yields more than that once nothing is dropped, and Neuroloom's own tree about 1,000. The extractor now writes files of at most 500 entries, gives every entry an id the API accepts (42 ids on Neuroloom's tree had characters it rejects, and one bad id fails a whole call) and unique within the run, and the port sends each file with `skip_deprecation: true`. Without that flag `sdlc_seed` marks every earlier seed memory the call leaves out as deprecated, whatever its version, and a weekly job deletes them: a second file retired the first, and a re-port after cleanup retired everything the cleanup had removed from disk.
- **The port and the migrate handlers keyed the same knowledge differently.** The port's extractor wrote `{domain}:{file}:{key}` ids; `knowledge-seed` and `knowledge-update` sent files through `document_ingest_batch`, whose parser keys entries `{file}:{key}` and collapses a keyed Markdown document to its last section. A migration after a port therefore found nothing it recognised, and either skipped upstream's changes or added a second set. Both handlers now run the same extractor in a new `--upstream` mode on z-sdlc's source at the target tag and send its files through `sdlc_seed` with `skip_deprecation: true`. `knowledge-update` lists what upstream removed for CD instead of retiring it, and keeps 0.6.1's rule for knowledge a project removed from Neuroloom. A project initialized or migrated before 0.7.0 may hold entries under the old ids too; they are left alone, and removing them is CD's call.
- **Initialize's own project content now goes through the `project-knowledge` phase** (z-sdlc contract 0024) as memories tagged `sdlc:project-specific`: each discipline's Project Context, Phase 8's knowledge entries and the Process Maturity Tracker. z-sdlc 3.0.0 graduates a lite install without the adapter, and the port brings it over afterwards. It replaces 0.7.0's earlier prose instruction to those phases. `knowledge-seed` removes and records the map, and removes Phase 1's copies of the files it seeds; upstream now skips Phase 5 and adjusts Phases 9a, 10 and 11 itself.
- **`CLAUDE.md`'s SDLC region in recoveries and audits.** Every restore now includes `CLAUDE.md`; the audit scans only the region between its markers, and a `CLAUDE.md` with no markers and a knowledge reference is a regression. The port asks which sections are z-sdlc's when the markers are missing and adds them, as `sdlc-migrate` §2.1e does.
- **Provenance, Gate 3 and audit details.** The provenance log is kept whenever an entry was not stored (a failure or a source mismatch). Gate 3 no longer keys its "not a re-port" case on `install_date`, which every file-mode manifest has. The count check uses `memory_get_index`, since `memory_search` returns at most 100. Stage 4g copies `.claude/agent-memory/` first, because git ignores it. The transformer can now call the tools its transform actions use (`document_ingest_batch`, `update_document_source_archive`).
- **`knowledge-update` would have overwritten the project's own knowledge corrections.** With the port and the handlers sharing ids, sending upstream's every entry put upstream's text over every entry the project had corrected (189 of them in Neuroloom's tree, against z-sdlc v2.12.2), and re-seeded entries the project had removed. `knowledge-update` now sends only what upstream added or changed between the project's `source_version` and the target (the extractor's new delta mode), sends a changed entry only when the workspace still holds upstream's previous text, and lists the rest for CD as conflicts or project removals. With no `source_version` it stops and asks. A workspace seeded before 0.7.0, under the old ids, is detected from a few probe ids, and the phase halts before any Neuroloom write and says the workspace needs a one-time conversion, instead of updating nothing.
- **Ported parking lots were invisible to the skills that read them.** The port stored each discipline file as one record without the `sdlc:parking-lot` tag. It now divides each file as z-sdlc's §2.3 does: the framework sections as `discipline:<name>:framework`, the entry the handlers update, and each parking-lot entry, Active Questions, Project Context and the maturity tracker as `sdlc:project-specific` entries. Records an earlier version stored stay until CD removes them.
- **Seed files had to fit the 1 MiB upload limit too,** and an HTTP upload that failed looked like a success: the extractor now packs by size as well as count (`--max-bytes`), and a file counts as seeded only when its response holds all four counts. The extractor refuses duplicate ids rather than pick a winner, writes no file when there is nothing to seed, and takes `--tag`, which `sdlc-ingest`'s transform now uses to seed what it adds through the same path, tagged `sdlc:project-specific`.
- **Seed labels and versions.** Initialize seeds the commit it installs (its `source_version`, or `HEAD`), labelled with that version; a migration labels the seed with the target tag. Spec-relevant domains are recorded in the manifest and their importance re-applied on each update. `project-knowledge` looks an item up before storing it again on a re-initialization. The port's `CLAUDE.md` region follows §2.1e's heading rule instead of only the sections with a match. A port that stopped after ingestion continues as a fresh port; the "partial port" mode is gone. The transformer's telemetry check no longer expects a Pass 2 event for exempt and no-pattern files. Pre-flight checks for `pyyaml`.
- **Knowledge updates decided by a tested script.** `knowledge-update` decides each new and changed entry with a tested script (`classify_knowledge_update.py`) instead of by hand: send, already current, conflict (including a project's own title on an entry upstream changed, since the server refreshes the title with the text, and a new upstream id the project already uses, such as Neuroloom's `U17`), or removed by the project; seed files are rebuilt from its list with the extractor's `--only-ids`. A missing or empty baseline now fails closed instead of making every upstream entry look new, and the baseline falls back to `source_version_sha`. A release with no knowledge change still moves the workspace's version marker, by re-sending one entry the workspace already holds unchanged. The id scheme is recorded in the manifest (`knowledge_id_scheme: 2`, written by `knowledge-seed` and `/sdlc-port`), so a workspace seeded before 0.7.0 is detected for certain, and `post-file-write` checks the marker and the baseline before the transformer writes anything. The port fetches upstream at the project's `source_version` and tags every entry upstream didn't have as `sdlc:project-specific`, labels its seed with that version, and no longer tags the project's fixed-id data (Active Questions, Project Context, the maturity tracker), so a re-port updates them; parking-lot entries keep the tag. `path-mappings.md`'s rewritten provenance row gets its own telemetry subtype, so the audit no longer expects a Pass 2 event for it. The port's `CLAUDE.md` markers are written only after the user confirms. Stage 3b states the tags the deliverable extractor really writes, and the Stage 2 count lists the docs it skips for having no frontmatter. `ingest_to_neuroloom` keeps the flat file unless something was seeded from it.
- **Re-ports and older workspaces.** A re-port refuses a workspace an earlier version ported (no `knowledge_id_scheme` marker): writing the marker over old records would leave them beside the new ones for good. Such a workspace, and a migration of one, halts before any Neuroloom write and says it needs a one-time conversion that this release doesn't do: replayed on the one such workspace, every rebuild from the project's files lost upstream entries added since those files and edits made only in Neuroloom. A re-port with no knowledge files left on disk (after the first port's cleanup) skips the seed and continues, since Neuroloom's copy is the live one. A re-port also refuses a project migrated since its port (`source_version` differs from `knowledge_seed_version`), since it would put older text back; it says that entries tagged `sdlc:project-specific` aren't updated by it, and skips Post-Port Cleanup, which could otherwise delete a file whose edits Neuroloom doesn't have. The classifier reports rows tagged `sdlc:project-specific` as protected rather than sending them, picks the no-op entry for the version marker itself (byte-equal, as the server compares), and the target side of a delta fails closed like the baseline. Version labels are consistent: a migration labels and checks `[target_tag]`, a port its `source_version`.
- **A port could write to the wrong workspace, or over records from before 0.7.0.** A re-port with no knowledge files left now skips the seed only when this workspace holds the sentinel (and, when the manifest records one, it is that workspace); otherwise it stops before any write, where the previous change would have written deliverable docs into whatever workspace the key reached. Gate 3 told a stopped port from other records by a tag the port never writes, and no id lookup can tell them apart (the 0.6.x port and stock z-sdlc share most ids). A fresh port now writes `port_in_progress`, with the workspace it writes to, to the manifest before its first Neuroloom write, so a stopped one is recognised locally and is continued only into that workspace (even when its first seed call failed and no sentinel exists yet), and Gate 3 stops on any sentinel the manifest doesn't account for, naming the workspace. Every re-port checks that the sentinel is in the workspace the manifest records, and compares `knowledge_seed_version` with the label rule rather than the raw `source_version`, so an untagged install can be re-ported. `knowledge-seed` writes its marker and workspace before seeding and halts on a workspace mismatch; a failed seed file keeps the run's writes, and the phase is re-run from the handler and `/sdlc-initialize` finished by hand, since a plain re-run reports "Already initialized". `knowledge-seed` halts a re-initialization over records from before 0.7.0, which it would otherwise have seeded beside and then marked.
- **`/sdlc-migrate` never checked which workspace the API key reached.** With the key on another project's workspace, `knowledge-update` would have rewritten that project's rows and moved its sentinel, and spot checks of knowledge ids pass there too, since every workspace holds most of the same ids. Every phase that writes to Neuroloom (`knowledge-seed`, `project-knowledge`, `knowledge-update`, and `post-file-write`'s early check on a migration) now compares the sentinel search's echoed `filters.workspace_id` with the manifest's and halts on a mismatch, on a missing id during a migration, or on a search error; the audit's Check 5 compares them too. The transformer's two Neuroloom writes, which run when a skill finishes, outside any phase (`ingest_to_neuroloom`, `sync_archive_status`), make the same check first. Whether a sentinel exists is decided by exact tag, not by the relevance-ranked search, which can miss one written moments ago. `knowledge-seed` no longer falls back to the clone's `HEAD` when the install's release doesn't resolve, and its recoveries re-run the whole section, including the workspace check and the map removal, before finishing `/sdlc-initialize` from Phase 5's adapter check.
- **Gate 3 is a tested script.** Three review rounds in a row found another gap in the prose that decided whether a port may write: a re-port with no recorded workspace, a re-port after a migration whose `source_version` hadn't moved yet, records an older port left without a sentinel. `skills/sdlc-port/scripts/decide_port_gate.py` now decides from the manifest and what Neuroloom shows (by exact tag), with a 39-row decision table in its tests. The skill gathers the facts and follows its output; a missing or failed fact stops it (exit 2) rather than reading as "nothing there".
- **`knowledge_id_scheme: 2` means the seed is complete.** Before the first write, `knowledge-seed` and the port record only an in-progress key and the workspace; the scheme marker is written after the last successful call. A migration of a half-seeded workspace halts instead of sending a delta and leaving the missing entries missing.
- **One recovery per operation.** Every halt in the handlers ends with the same recovery for its operation: a migration saves every change first (a patch and copies of new files, under `.git/sdlc-undo/`), then undoes only a run CD confirms began on a clean tree (git overrules a yes when it shows uncommitted work outside the paths a migration writes), and otherwise changes nothing but the manifest upstream already rewrote, since upstream has no dirty-tree check and git can't tell a run's writes from uncommitted work that was already there; an initialize keeps its writes, goes back to the start of the upstream phase that called the halted handler (upstream hands some handlers one item at a time), and is finished by hand from its SKILL.md, with how to find the plugin directory and a clone that has the install's release. The id-probe halt (which a project's own removals tripped) and the "confirm a full re-seed" option are gone. A manifest with this plugin's adapter block but no `neuroloom_backend` is an unfinished initialize whatever its scheme marker says, so a migration halts there instead of passing and then failing its audit on every re-run. `project-knowledge` gives each item a stable key tag, so a phase re-run updates in place.
- **Migrations could overwrite project-assessed data.** A discipline's status line rode in its framework entry, so an upstream change replaced the project's own assessment (z-sdlc §2.3 calls it project data); it is now its own entry, and no project-data entry (status, parking-lot structure, Active Questions, Project Context, the tracker) ever appears in a delta. Also in the scripts: a malformed target file is fatal in delta mode instead of being reported as removed; the fixed-id exception applies only to discipline ids; repeated Project Context sections are all kept; an entry too large for one call fails instead of producing a batch the API rejects; the classifier keeps indentation significant (a dropped final newline still matches); and the no-op send has fifty candidates instead of eleven.
- **The port could lose or misfile edits.** A failed upstream fetch now stops the port (tags can't be added to rows later); cleanup is skipped on a continued port, whose earlier run may not have stored a later edit; `CLAUDE.md` is restored from a copy, not `git checkout`, so edits outside the SDLC region survive; the port wires the skill transforms it used to leave to the next migration; and a count shortfall or checklist failure restores the pre-port manifest. The transformer ingests only files the skill wrote this run, needs the scheme marker, labels its seed with the sentinel's release, and keeps a file whenever any entry came back `unchanged`, except a parking-lot bullet, whose id is a hash of its own text.
- **Rare states in migration and initialize recoveries.**
  - **Manifest snapshot.** The first handler of a migration snapshots the manifest, so even a dirty-tree undo restores it with its uncommitted keys.
  - **Recovery clone.** The clone used for an initialize recovery is checked out at the release.
  - **Seeding into an emptied workspace.** `knowledge-update` won't send a delta into a workspace whose sentinel is gone, and the pre-seed check refuses records with no recorded workspace.
  - **Initialize's workspace.** Initialize never overwrites the workspace `knowledge-seed` recorded.
  - **Exact-tag checks.** The re-seed check, the port's discipline check and the first-run sentinel check use exact tags.
  - **`CLAUDE.md` restore.** Only the SDLC region comes back from the backup.
  - **`sdlc-ingest`.** It seeds only the files the skill's own report names.
  - **No-version-key re-port.** It keeps its recorded label.
  - **Gate facts.** Gate 3 rejects non-boolean manifest flags and a `ported_at` without its backend key.
  - **Extractor.** It decides project data by where an entry came from, not its id, no longer reads an id ending `:unparsed` as a parse failure, treats an unreadable target file as fatal in delta mode, and no longer refuses a delta that has no probe ids.
  - **Telemetry count.** It allows a release that changed only scripts.
- **Ingest stubs, snapshots and extractor checks.**
  - **Discipline stubs.** A discipline stub `sdlc-ingest` created is moved out of the extractor's reach on any halt, so a re-port can't read it as the framework entry. The ingest report says whether each file was created or appended to.
  - **Manifest snapshots.** The stale-sentinel recovery restores the manifest from the run's snapshot, not git. Outside git, a migration's undo restores the manifest from its snapshot and then deletes it; an earlier run's snapshot is kept, listed for CD, since a run that crashed mid-rewrite may have left the only good manifest.
  - **`CLAUDE.md` region.** The region file records line numbers, so a repeated heading can't mislead a restore.
  - **Extractor.** It now fails on an unreadable file or a dangling symlink in every upstream mode, and excludes project data by kind even when a long stem's id is hashed. The re-seed check uses the id the extractor produced (`framework_ids`) instead of rebuilding it from the filename.
  - **Smaller fixes.**
    - The no-sentinel recovery also probes `sdlc:knowledge`.
    - The initialize checklist uses an exact tag.
    - The `CLAUDE-SDLC.md` lookup uses the `v`-prefixed tag.
    - A stopped port's ingest halt says to resume `/sdlc-port`.
- **What a re-port re-sends.** A re-port re-sends only knowledge entries and parking-lot bullets (`--exclude-kinds`), never a discipline's framework, status, Active Questions, Project Context or tracker: after the first port their live copy is Neuroloom's, so an ingest stub on disk, committed or not, can't overwrite them. Ingest never sends an entry whose id has the shape of a fixed discipline id, whatever file it came from, and treats a file its report doesn't mark created or appended as created. A created stub is renamed on every halt; its recovery merges into an existing file and reports it as appended, and a failed rename halts. The `CLAUDE.md` region file is written before the markers go in, with line numbers counted in the copy, and both ends are found at their recorded lines. An earlier migration's manifest snapshot outside git is never deleted automatically. The extractor refuses, in every upstream mode, a target directory that is missing, a broken or escaping symlink, or empty, refuses a dangling symlink in the baseline, and scans only the files it would read.
- **What a knowledge file may not claim.** A knowledge entry whose id falls in the `discipline:` namespace (written in the file, or spelled by its path) stops the extractor in every mode, since Neuroloom matches by id alone and it would overwrite that discipline's entry. So does an item carrying a tag Neuroloom adds itself (`sdlc:knowledge-id:*`, `sdlc:seed`, `sdlc:seed-version:*`, `sdlc:sentinel`, `sdlc:deprecated`), which could make one row stand in for another; `--tag`/`--tag-new` refuse the same set. A `tags` value that would become an entry's tags (on an entries, rules or gotchas item) must be a list of strings: a scalar, `tags: off` (YAML's `false`) or `[on]` is refused instead of crashing, sending one-character tags or silently taking the defaults. Any other `tags` key is content, so a knowledge document describing a schema can't block initialize or migrate. Each refusal's advice depends on where the id came from, and every refusal is reported in one run.
- **The port undoes itself from its own copies, never git.** Each run fixes one `<undo>` in the git directory (`.sdlc-port-undo/` outside git) at the start of Stage 4c and keeps its whole undo state there: a copy of each file before its first edit (agent memory included), the list of files it created, and Stage 5's own manifest snapshot. Stage 4d's validation restore, the audit-, checklist- and count-failure recoveries, and abandoning a run all restore from it, so an uncommitted edit in a transformed file, every file the port didn't touch, and notes another session added to agent memory survive; abandoning a run restores that run's own manifest snapshot even after a retry or a truncated write, later runs first. A passing audit, and every completed whole-run undo, deletes the run's `<undo>`, so no later recovery applies it again; after a passing audit the pre-port `knowledge-routing.md` the port replaced is kept under `sdlc-port-kept/` first, and nothing is deleted if that move fails. `CLAUDE.md`'s copy is never replaced: a leftover one is set aside under a timestamped name, and the current file is copied aside before a continue or a restore. The port states its precondition: no other session changes the project's records or files while it runs.
- **Stage 5's hashes keep the project's edits visible.** Stage 5 rehashes a file only when the run created it or its pre-edit copy matched its hash in the pre-run manifest; a file that held the project's own edits, or an earlier attempt's transform, keeps its hash, so the next migration asks about it rather than overwriting. The port's Check 4 treats such a kept hash as a WARN.
- **Agents get the Neuroloom tools their text calls, and the read tools their memory calls.** The port grants each agent that calls a Neuroloom tool its profile's tools plus any other it calls, whichever attempt transformed it and including agents whose memory Stage 4g rewrites; migrate's tool injection does the same, reading the agent's memory too, so an upstream frontmatter rewrite can't drop one. From memory, beyond the agent's profile, only the read tools `transforms.yaml` → `memory_grant_tools` lists are granted: agents write their own memory, so a note can't give an agent a tool that writes. A failed edit to an agent's tools line is named in the port's final summary with the tools to add by hand. Every profile includes `memory_get_index` (the rewritten provenance and project-knowledge reads), and the profiles that store include `memory_update`.
- **Smaller fixes.** A continued port records the `CLAUDE.md` region approved in that run. The stale-sentinel recovery follows migrate's recovery, which saves the tree, the manifest itself included, before putting the manifest back.
- **Every session would have said an update was available.** The API's version endpoint strips the tag's leading `v`, while the knowledge handlers now label seeds with the git tag, so the SessionStart hook's exact comparison never matched. It compares without the prefix now.
- **Halts say how to undo what upstream already wrote.** `sdlc-migrate` writes scripts, YAML and the first `.md` before any adapter phase can halt; every halt message now names its operation's recovery: a migration saves every change first and undoes only a run CD confirms began on a clean tree; an initialize keeps its writes and is finished by hand.
- **The `/sdlc-initialize` recovery deleted the project's agents.** It ran `rm -rf .claude/sdlc/ .claude/agents/`, which removed every agent the project already had. On an `ops/sdlc` project it also left the SDLC tree in place. It now undoes nothing: a halted initialize keeps its writes and is finished by hand from the start of the phase that halted (z-sdlc's transaction log records counts, not paths, so no undo could tell its writes from the project's). Found by the Sleeved migration's reviewers.
- **An audit over a missing root could pass.** grep over a path that does not exist finds nothing, so a scan of the wrong root reported clean. Check 4 now fails when `ops/sdlc/` is missing, and a grep error on it counts as a regression.

### Added

- **An SDLC root check** (`references/preflight.md` check 0). It fails when `.claude/sdlc/` holds any tracked or new, unignored file, even beside `ops/sdlc/` (ignored leftovers such as `.local/` don't count, so an old worktree's local state doesn't trip it), when the manifest or the migration names another root, or when the manifest still keys files by `.claude/sdlc/` paths (a stale `declined_files` key would re-seed knowledge CD declined). Its message says how to move. Without it, an unmoved install would get audits that scan a directory that isn't there and pass. `/sdlc-port` runs it in Stage 1. z-sdlc doesn't run `preflight.md` itself, so the `knowledge-seed`, `knowledge-update` and `post-file-write` handlers each run it as step 0 and halt the operation if it fails, whichever of them fires first.

### Known limits

- **`/sdlc-initialize` under z-sdlc 3.0.0 has been checked by review, not by a run.** z-sdlc 3.0.0 finds the adapter before Phase 1's copies, so this plugin's `post-file-write` now runs on each of them, before the project's agents and `CLAUDE.md` exist. Review found and fixed three gaps there; an end-to-end run on a scratch project is still to do. `/sdlc-migrate` and `/sdlc-port` are the paths in use today.
- **The port's undo is prose.** A crash at an exact moment (mid-copy, mid-delete, mid-write) can leave a run's undo state incomplete. Moving undo and restore into a small tested script, as Gate 3 was, is the follow-up.

## [0.6.1] - 2026-11-23

### Changed

- **The content-merge audits read z-sdlc's replacement and removal marks** (z-sdlc contract 0021). A section a `PROJECT-SECTION-START: <label> replaces` block stands in for, or a `PROJECT-SECTION-REMOVED` line names, is absent by the project's marked choice: neither the structural count nor the mandatory-step check reports it as a regression. The marker audit counts removal lines with the blocks, so a lost removal mark halts like a lost block.
- **Knowledge files a project declines stay declined** (z-sdlc contract 0022, `.sdlc-manifest.json` → `declined_files`). `knowledge-seed` skips a declined path and records each file its applicability check removes. `knowledge-update` leaves declined files out, and no longer re-seeds a file the project removed from the workspace (absent there, present upstream at the project's `source_version`): it reports it for CD to decline or re-seed.
- **The compliance auditor's new sections are transformed and checked** (z-sdlc 2.9.6 gave `sdlc-compliance-auditor` a Knowledge Context and a Communication Protocol section). The Knowledge Context line matched an existing row. A new mapping row covers the Communication Protocol line's "…and follow the handoff contract it defines". The post-operation audit's minimum-MCP list now expects a call in each of the two sections, not one anywhere in the file.
- **`knowledge-seed`'s spec-relevance question has a path for a run with no ask tool** (headless, or `sdlc-initialize` run inside a subagent, z-sdlc `process/headless-mode.md` § Subagents): it boosts nothing and lists the question in the run's result with a proposed set. Nothing later depends on it, so the run doesn't stop.
- **`knowledge-update` tells the migration to skip `sdlc-migrate` §3.3's map updates and never create the map.** z-sdlc 2.9.6 added an `sdlc-reviewer` role and a new mapping, which would send a migration to edit, or create, a map a Neuroloom project doesn't have. z-sdlc's §3.3 now says the same, but a project runs the `sdlc-migrate` it has installed, so the handler gives the instruction until the project has a copy with z-sdlc's line.
- **Supports z-sdlc 2.9.10** (`adapter.json`, both keys, and `.claude-plugin/plugin.json`, whose `supported_zsdlc_version` had drifted to 2.2.0). The `[contract-change]` entries since 2.2.0 are covered: 2026-11-14's knowledge-store glob, which the mapping table already transformed, and 2026-11-20's marks and declined files, above. No release from 2.9.1 to 2.9.10 adds one; the entries above cover the adapter-facing changes those releases made.

### Fixed

- **The post-operation audit's manifest check would report false regressions on a migration.** z-sdlc runs the adapter's `post-operation` phase before its manifest update (`sdlc-migrate` §4.4a, then §4.5), but the audit assumed the manifest was written: it expected the target `source_version`, a `last_migration` timestamp z-sdlc never writes, and the new hashes of the files the run wrote. Found by reading the two docs side by side, not in a run's report. On a migration it now compares the run's target tag with the version `knowledge-update` re-seeded at (a difference is a WARN), skips the hashes of every file the run touched, and lists a mismatch on an untouched file as pre-run drift (WARN).

## [0.6.0] - 2026-10-30

This is the first changelog for this plugin; earlier releases are in the git history.

### Breaking Changes

- **The two CI-mode SessionStart lines are a contract, and changing their wording is a breaking change.** Factory workflows and tests match them byte-for-byte. A wording change will be announced here under "Breaking Changes".
- **In CI mode the plugin must be pinned together with `neuroloom-claude-plugin`, at versions that list CI mode in their changelog.** An older SDLC plugin on a newer base plugin fails open: its `post_tool_use` knows nothing about CI mode and still ingests deliverable documents. The reverse pairing is safe (see "Added", version skew).

### Added

- **CI mode** (`NEUROLOOM_MODE=ci`, defined by the base plugin; unset or blank is normal mode and any other non-empty value also means CI). In CI mode:
  - `session_start` still makes its two reads (the latest z-sdlc version, then the workspace sentinel), each with a 10 s timeout, and ends silently on an unreachable API or a non-200 answer. Up to date is silent, as is a sentinel with no `sdlc:seed-version:` tag. The two messages that tell a person to run `/sdlc-initialize` or `/sdlc-migrate` are replaced by two neutral lines, so an unattended agent is not nudged into running a skill that writes tracked files:
    - `[Neuroloom SDLC] This workspace has no SDLC knowledge seeded. No action is taken in CI mode.`
    - `[Neuroloom SDLC] Workspace SDLC knowledge is at {workspace_version}; latest is {latest_version}. No action is taken in CI mode.`

    Control characters in the two versions are escaped and each version is cut to 64 characters, so the line stays one line.
  - The SDLC hooks need the key already seeded into `<project root>/.neuroloom.db` by the **base** plugin's `scripts/seed_project_key.py`; this plugin has no seed step.
  - `post_tool_use` returns before it reads the file, opens a database or starts a thread. Nothing is sent and nothing is recorded.
  - `run_hook.py` finds the base plugin **only** through `NEUROLOOM_CLAUDE_PLUGIN_ROOT`, which must be set to an absolute path of a directory holding a `pyhooks/` package with `__init__.py` and `config.py`. It never searches `~/.claude/plugins/cache` and never falls back to the sibling checkout. If the check fails it prints one stderr line and exits 0, so the hooks do nothing.
  - The hook runs under `sys.executable` (no venv lookup, no degraded-venv line) and is started with `python -I`, so a planted `pyhooks/`, `sdlc_pyhooks/` or `json.py` in the checkout is never imported. `PYTHONPATH` from the environment is ignored; the import path is exactly this plugin's root and the base plugin root.
  - If the base plugin cannot be imported, each hook prints `[neuroloom-sdlc] CI mode: base plugin import failed (<ExceptionTypeName>); hooks do nothing` to stderr (the exception type only) and exits 0.
- **Version skew fails closed.** `sdlc_pyhooks.mode_state()` returns `normal`, `ci` or `skew`. It reads `NEUROLOOM_MODE` from the environment and checks that the base plugin's `Config` declares `ci_mode`. When the environment says CI and the base plugin cannot report it (too old, or not importable), both hooks do nothing: no database, no API call.

### Changed

- CI mode has been developed and checked on macOS with Claude Code 2.1.314; the z-sdlc smoke job in GitHub Actions has not run yet, and Windows is untested.
- Four copies of the `NEUROLOOM_MODE` parse rule exist (base `config.py`, base launcher, this launcher, `sdlc_pyhooks`); `tests/test_mode_parser_agreement.py` keeps them in agreement.
- The README paragraph that told you to leave `NEUROLOOM_CLAUDE_PLUGIN_ROOT` unset is corrected: leaving it unset is still right for attended sessions on a marketplace install, but in CI mode the variable is required.
- Outside CI mode nothing changes in the SDLC hooks, except through the base plugin: they read the key through `config.load()`, so they inherit the base plugin's project-root cutover (the key and state come from `<project root>/.neuroloom.db`, not the directory Claude is in). See the base plugin's changelog.

### Fixed

- The README's endpoint table listed `POST /api/v1/memories/search` for the SessionStart sentinel lookup; the hook calls `GET /api/v1/memories/?tags=sdlc:sentinel&limit=1`.
